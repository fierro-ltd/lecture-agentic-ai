# v0.11.0 Design Spec — Stabilize & Complete the Loop

**Date:** 2026-04-01
**Target:** v0.11.0
**Branch:** `feat/v0.11-stabilize-and-complete`
**Scope:** Phase 1 (6 stabilization tasks) + Phase 2 (6 feature completion tasks)

## Context

lecture-agentic-ai integrates Paperclip, Hermes Agent, and Temporal into a per-customer agentic AI platform. The v0.10.0 baseline deployed successfully but has infrastructure fragility (missing healthchecks, no API auth, manual SOUL.md seeding) and incomplete user-facing features (no reviewer UI, no notifications, single industry template).

This spec covers the work needed to make the platform demo-ready for cross-industry customers.

## Deployment Model

- One instance per customer (university, hospital, government body)
- "Companies" in Paperclip = departments within that institution
- Platform-level code uses industry-neutral terminology
- Industry-specific terms belong only in company templates and Hermes skills

## Constraints

- Do NOT modify upstream Paperclip or Hermes source code
- All services run via Docker Compose
- LLM: OpenCode Go GLM-5 (text), OpenRouter Gemini (vision)
- Never pass `OPENROUTER_API_KEY` to Paperclip container
- Each logical change gets its own commit

## Phase 1: Stabilize

### 1.1 Hermes Gateway Healthcheck

**Problem:** `hermes-gateway` has no healthcheck. Dependent services start before the gateway accepts requests.

**Solution:**
- Add healthcheck to `hermes-gateway` in docker-compose.yml using `curl -sf` against `/health` with Bearer auth
- Use `$$` to escape env var expansion in YAML
- Change `hast-api`, `hast-worker`, `paperclip` depends_on to `hermes-gateway: condition: service_healthy`
- `start_period: 20s`, `interval: 10s`, `timeout: 5s`, `retries: 10`

### 1.2 Harden Temporal Startup

**Problem:** Temporal's `start_period: 30s` is often too short. HAST services crash if Temporal isn't ready.

**Solution:**
- Bump Temporal healthcheck `start_period` to `60s`
- Add retry logic to `get_temporal_client()` in `hast/src/api.py`: exponential backoff (3 attempts, 5s/10s/20s delays) using lazy initialization
- Log connection attempts for observability

### 1.3 HAST API Authentication

**Problem:** All HAST API endpoints are completely open.

**Solution:**
- Add `HAST_API_KEY` env var to `hast/src/config.py` (default: same as `HERMES_API_KEY`)
- Create FastAPI dependency `verify_api_key()` that validates `Authorization: Bearer <token>`
- Apply to all `/api/*` routes; leave `/health` open
- Pass `HAST_API_KEY` to `hast-api` and `hast-worker` in docker-compose.yml
- Update `docs/API.md` with auth requirement and example headers

### 1.4 Lock Down CORS

**Problem:** `allow_origins=["*"]` in HAST API.

**Solution:**
- Add `CORS_ALLOWED_ORIGINS` env var (comma-separated)
- Default: `http://localhost:3100,http://localhost:3200,http://localhost:8233`
- Parse to list, pass to `CORSMiddleware`
- Add to `.env.example` with explanatory comment
- Include reviewer-ui port (3200) in defaults

### 1.5 Automate SOUL.md Seeding

**Problem:** Agent instructions must be manually pasted into each Paperclip instance's UI.

**Design decision:** Direct database approach (option A). More reliable than browser automation, no UI dependency. Acceptable coupling to Paperclip schema for a PoC.

**Solution:**
- Create `scripts/seed-agent-instructions.py`:
  - Reads all `hermes/agents/*/SOUL.md` files
  - Connects to Paperclip PostgreSQL database
  - Discovers schema (inspect tables to find agent instructions column)
  - Updates agent instruction fields to match SOUL.md content
  - Idempotent (safe to run multiple times)
  - Matches agents by slug/name convention
- Add `seed-instructions` one-shot service to docker-compose.yml:
  - `restart: "no"`
  - Depends on `postgres: service_healthy` and `paperclip: service_started`
  - Runs after Paperclip has initialized its schema
- Document in README that SOUL.md changes are auto-applied on startup

### 1.6 Fix Production 403

**Problem:** `https://lecture-agentic-ai.fierro.co.uk/` returns 403 Forbidden.

**Solution:**
- Investigate Caddyfile configuration
- Check `PAPERCLIP_DEPLOYMENT_EXPOSURE=private` interaction with Caddy reverse proxy
- Likely fix: change exposure to `public` or adjust Caddy config
- Verify fix on production after deployment

## Phase 2: Complete the Working Loop

### 2.1 Reviewer Dashboard

**Problem:** Human reviewers have no UI to see pending reviews or act on them.

**Design decision:** Standalone static SPA, not embedded in Paperclip (no upstream modification). Can be branded per customer.

**Solution:**
- Create `reviewer-ui/` with:
  - `index.html` — single-page app
  - `styles.css` — EDT/Lecture visual language
  - `app.js` — API client and UI logic
  - `nginx.conf` — static file serving
  - `Dockerfile` — nginx-based container
- Features:
  - Lists submissions with status "review" (GET `/api/submissions?status=review`)
  - Shows AI evaluation details for each submission
  - Approve / Reject / Request Revision buttons with notes field
  - Authenticates with HAST API key (configurable)
- Industry-neutral language: "Reviewer" not "Professor", "Submission" not "Assessment"
- Add as service in docker-compose.yml on port 3200
- Update README services table

### 2.2 Review Notifications

**Problem:** Nobody is notified when reviews are ready. Reviews expire silently at 7-day timeout.

**Design decision:** Webhook pattern over email for cross-industry flexibility.

**Solution:**
- Add `NOTIFICATION_WEBHOOK_URL` env var to HAST config
- When submission enters "review" status, POST JSON payload to webhook URL
- Add 24h-before-expiry reminder as parallel Temporal timer within `ReviewWorkflow.run()`:
  - After entering wait state, schedule timer at `timeout - 24h`
  - Timer fires webhook with "expiring soon" payload
- Webhook payload: `submission_id`, `submission_type`, `entity_id`, `status`, `review_url`, `deadline`, `ai_evaluation_summary`
- No-op if `NOTIFICATION_WEBHOOK_URL` is unset
- Document webhook format in `docs/API.md`

### 2.3 Demo Scripts

**Problem:** No demonstration of external systems feeding work into the platform.

**Solution:**
- `scripts/demo-routine.sh`:
  - POSTs to HAST API to create submission with sample data
  - Prints submission ID and workflow ID
  - Optionally polls for status updates
- `scripts/demo-review.sh`:
  - Takes submission ID as argument
  - POSTs approval to `/api/submissions/{id}/review`
- Update `docs/DEMO_SCRIPT.md` with complete walkthrough

### 2.4 Healthcare Company Template

**Problem:** Only one company template (higher-ed). Multi-company model isn't demonstrated.

**Solution:**
- Create `paperclip/company-templates/healthcare/company.json`:
  - Clinical Operations Director (CEO-equivalent)
  - Documentation Quality Agent
  - Compliance Agent
- Write SOUL.md files:
  - `hermes/agents/clinical-ops-director/SOUL.md`
  - `hermes/agents/documentation-quality/SOUL.md`
  - `hermes/agents/healthcare-compliance/SOUL.md`
- Create healthcare skill: `hermes/skills/clinical-documentation-review/SKILL.md`
- Update `docs/CUSTOMIZATION.md`

### 2.5 Neutralize Platform Language

**Problem:** HAST code and docs use education-specific terms.

**Solution:**
- Audit `hast/src/models.py` and `hast/src/api.py` for education-specific terms
- Existing terms (submission, evaluation, review) are already neutral — verify and fix any that aren't
- Update docs (ARCHITECTURE.md, API.md, WORKFLOWS.md) with generic or multi-vertical examples
- Add cross-industry section to README

### 2.6 Structured Logging

**Problem:** No structured logging. Debugging requires reading individual container stdout.

**Solution:**
- Add `python-json-logger` to `hast/requirements.txt`
- Configure JSON logging in HAST API and Worker
- Every log line includes: `timestamp`, `service`, `level`, `message`
- Contextual fields when available: `submission_id`, `workflow_id`, `correlation_id`
- Add `X-Correlation-ID` header middleware that flows through API requests and into Temporal workflow context
- Auto-generate correlation ID if not provided by caller
